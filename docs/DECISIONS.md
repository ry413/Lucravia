# Decisions

## 使用 Android MediaProjection，不使用 Accessibility Service

**Decision:** 屏幕输入使用用户明确授权的 Android MediaProjection API。

**Reason:** 产品只需读取像素，不需要也不应获得操作其他 App 的能力。

**Consequences:** Android 14+ 每次捕获会话都需要用户重新同意；捕获期间必须保持 `mediaProjection` 前台服务。
为避免单应用选择器冷启动目标 App 时的后台启动竞态，宿主 Activity 会在打开选择器前先以 `location` 类型预启动服务；获得授权后才升级为 `mediaProjection|location`。用户取消授权时必须立即停止该预启动服务。

## 使用 DashScope qwen3.7-flash 进行整屏视觉识别

**Decision:** Python 局域网服务使用 DashScope OpenAI 兼容接口与 `qwen3.7-flash`，关闭思考并启用 JSON Mode；Android 不再直连 DashScope。

**Reason:** 实机滚动后，本地 OCR 的小字、边界框和跨卡片归属不稳定。整屏 VLM 能同时理解卡片边界与字段语义。

**Consequences:** DashScope Key 只存在于服务端 `.env`，APK 只包含局域网 URL。识别依赖手机能访问服务端且服务端能访问 DashScope。

## 开发期使用零依赖 HTTP 服务与共享密钥签名

**Decision:** 服务端使用 Python 标准库 `ThreadingHTTPServer`，接受原始 JPEG，并提供 `/health`、`/v1/analyze` 和 `/v1/cancel`；Android 和服务端从各自 `.env` 取得同一 `SHARED_SECRET`，POST 以 HMAC-SHA256 签名，并附带短时效时间戳与唯一请求 ID。

**Reason:** 测试期只分发给少量可信用户，优先降低部署和调试复杂度。签名不会在每个请求中直接发送密钥，且能在产生 DashScope/高德费用前拦截公网扫描器与简单重放。

**Consequences:** 手机和服务器时钟需保持在 5 分钟内；更换密钥后必须重新构建 APK。密钥可能被从 APK 提取，HTTP 也不保护截图与定位的机密性；公网测试应配 HTTPS，正式部署再引入可撤销的设备凭据、限流和持久化指标。

## 原生服务持有悬浮窗

**Decision:** 悬浮窗由 Android `ScreenCaptureService` 而不是 Flutter Activity 创建和更新。

**Reason:** 用户切换到司机端后 Flutter Activity 位于后台，而前台服务才是屏幕捕获会话的真实所有者。

**Consequences:** Flutter 通过 EventChannel 获得最近分析结果，但悬浮显示不依赖 Flutter UI 生命周期。

## 使用可移动的小状态胶囊反馈运行阶段

**Decision:** 屏幕分析期间保留一个固定小尺寸、可拖动的原生状态胶囊，显示等待稳定、识别中、结果数量、无完整单和请求失败；不恢复原先遮挡较大的多行结果窗。

**Reason:** 只有卡片框时，等待画面变化或网络请求期间没有任何可见反馈，用户无法判断服务是否仍在运行。小窗口足以表达状态，并允许避开关键订单内容。

**Consequences:** 小窗自身消费拖动手势，屏幕其余区域不受影响；其实时矩形必须从每一帧指纹中屏蔽，防止文字更新自触发。浮窗仍会进入 VLM 截图，用户应将它移到不遮挡订单字段的位置。

## 由服务端用高德两段驾车路线计算有效时薪

**Decision:** Android 将分析时的 WGS84 当前位置随截图发送给局域网服务。服务端转换为高德坐标，从已知起点附近搜索 POI，以平台接驾/行程里程辅助候选选择，再以路径规划 2.0 默认推荐策略分别计算接驾和载客路线。每段高德路线须通过与平台显示里程的宽松数量级审计；明显冲突标记 `route_mismatch`，不计算时薪、不参与推荐。有效时薪使用两段原始秒数加固定 3 分钟等客计算；两段路况、红绿灯和收费作为可解释的独立事实展示，不额外重复扣减时薪。

**Reason:** 平均速度无法反映拥堵和道路结构，平台显示的接驾分钟也不能替代载客路线 ETA；两段统一由正规地图服务计算，评价才有可解释的时间依据。拥堵里程和红绿灯还有能耗、疲劳与接驾取消风险，不能只藏在 ETA 中；收费由谁承担依平台规则而异，因此先展示而不武断视作司机成本。

**Consequences:** Android 需要前台定位权限，当前位置和订单地址会发送给高德。UI 展示两段 ETA、固定等客时间和高德匹配名称；API/地点失败显示“待算路”，里程冲突显示“地图地点匹配异常”，均不回退到 32 km/h 粗估。审计容差 `max(5 km, 平台里程的 60%)` 只拦截数量级错误，不以是否跨城或订单价格作为硬判据：真实 500 公里平台单与约 500 公里地图路线仍可通过。不同订单并行推进以控制额外延迟，但客户端按高德服务类别限速至低于个人认证默认 3 QPS，并对 10021 退避重试。

## 只为稳定且未提交过的新画面调用 VLM

**Decision:** 手机本地以低分辨率亮度指纹检测滚动和内容变化。连续两帧稳定、且与上次提交画面不同才调用 VLM；每台设备最多一个在途请求。目标 UI 的顶部 18% 不参与指纹，以排除动态倒计时。

**Reason:** 截屏可以高频执行，但模型不应处理滚动中间帧、动态倒计时或相同静态页面。

**Consequences:** 页面停稳后约两个采样周期才发起请求；静态页面不重复计费，失败请求按 3 秒退避。

## 排除顶部倒计时并使用稳定画面指纹

**Decision:** VLM 接收用户选择的全宽纵向屏幕区域，未校准时接收完整屏幕。低分辨率画面指纹将屏幕顶部 18% 和底部 8% 换算到选区局部坐标后忽略；订单描边和评价标签使用可截屏的普通窗口，并由指纹守卫显式屏蔽。

**Reason:** 司机端顶部“x 秒后将刷新”持续变化，但它既不是订单数据，也不应触发新一轮 VLM 请求。

**Consequences:** 顶部倒计时和卡片评价框不应触发额外请求；滚动、平台刷新或订单内容变化会自动产生一个新的稳定画面请求。

## 只支持目标司机端当前 UI 模板

**Decision:** 当前 VLM 提示词不尝试通用化，只描述目标司机端 UI、订单卡片字段以及禁止跨卡片拼接的规则。

**Reason:** 固定裁剪和整屏数字顺序在滚动、涨价文字和相邻卡片中表现不稳定；当前产品范围已明确只需支持该版 UI。

**Consequences:** 当前版本更能容忍滚动位置和文字边界变化，但目标软件大幅修改卡片结构后仍需更新提示词与回归截图。

## 扫描区域由用户在目标页面直接校准

**Decision:** 扫描区域固定为屏幕全宽。助手先显示一个仅占小块屏幕的“开始校准”浮窗，允许用户正常打开目标 App；点击后才显示全屏浮层拖动上下边界并在目标页面保存或取消。最小高度为屏幕 25%，保存为 0–1 归一化比例；校准期间不允许屏幕分析运行。

**Reason:** 不同手机状态栏、导航栏、显示缩放和目标 App 布局会改变有效订单区域。在 Flutter 设置页填写百分比难以对应实际画面，直接叠加在目标页面上调整更直观。

**Consequences:** 截图裁剪、稳定指纹、VLM 边界框和绿色提醒框必须共享同一 `ScanRegion` 坐标换算。缩小区域还能进一步降低视觉 Token，但选区边缘切到卡片时，该卡片会按严格完整性规则被排除。

## VLM 粗定位订单，客户端只做提醒

**Decision:** VLM 为每张卡片返回 `screen_rank` 和 0–1000 归一化 `bbox_1000`。客户端为最多三张完整订单分别绘制不可触摸的窄边框，并把排行、高德有效时薪及 `接驾+等客+行程` 时间拆分贴在对应框上；用声音和振动唤起注意，不根据坐标点击。

**Reason:** 用户需要立即知道推荐的是屏幕上哪张订单；固定 UI 下卡片级粗定位足以用于视觉提醒，但不具备自动操作所需的确定性。

**Consequences:** 无效或缺失坐标的订单仍保留在 Flutter 结构化结果中，但不画目标框。运行时不再显示遮挡订单的大型状态窗；多框显示期间暂停 VLM，忽略所有框线和标签像素并监测其余画面，页面变化后撤框并重新等待稳定。

## 用降低像素数而非只压 JPEG 优化 VLM 延迟

**Decision:** VLM 截图最大宽度由 1080 降为 720 px，JPEG 质量由 86 降为 72；DashScope `max_pixels` 设为 1,310,720，即 Qwen3.7 的 1280 个视觉 Token 上限。

**Reason:** DashScope 文档说明 Qwen3.7 每个视觉 Token 对应约 32×32 像素。实测平均总请求 4839 ms 中 DashScope HTTP 占 4794 ms，而冷连接 DNS/TCP/TLS/错误响应约 158 ms；压缩字节只能减少很小的网络部分，减少视觉 Token 才可能降低云端预处理和推理量。当前固定 UI 的关键数字较大，720 px 是保守的第一档。

**Consequences:** 真机日志中总输入 Token 从 2723 降至 1331；首批 9 次非空订单平均总延迟从旧版 4396 ms 降至 3242 ms，中位数约 3018 ms。必须继续验证小字、地点和边界框准确率；如明显退化，应先回升至 840 px，而不是继续降低 JPEG 质量。

## 完整订单要求显式可见性和两个地址

**Decision:** VLM 对每张卡片返回 `is_fully_visible` 与 `occluded_fields`。客户端只有在可见性为真、遮挡列表为空、四个关键数值及起终点原文全部存在时才认定订单完整。

**Reason:** VLM 可能根据露出的小数部分或 UI 模式脑补被遮住的整数；仅检查最终数值非空无法区分读取与猜测。缺少起点或终点也无法可靠判断订单价值或后续进行路线计算。

**Consequences:** 数字字段仍宁可漏掉边缘卡片，也不使用疑似补全结果。地址仅轻微裁到字形边缘但所有字符仍可可靠辨认时允许通过；存在字符缺失或歧义时仍排除。

## 地址纠错保留原文并限制改写

**Decision:** VLM 同时返回地址原文和 normalized 值，只允许非常明确的错别字、重复字与空格修正。客户端保留原文；normalized 与原文长度差超过 2 个字符时自动拒绝。

**Reason:** 语言模型适合做轻量文本规范化，但 POI 名称可能本来就不常见，不能让纠错变成地点猜测。

**Consequences:** UI 和后续地理编码优先使用通过校验的规范化地址，同时原始识别文本始终可追溯；不确定时两者相同。

## 自托管客户端更新并固定发布身份

**Decision:** Android 正式应用 ID 使用 `com.lucravia.xiaozhuiot`，从 `1.1.0+2` 起使用一把永久自管 Release Key。客户端通过现有服务的鉴权 GET 接口检查和下载 `server/updates` 中的 APK，校验大小与 SHA-256 后交给 Android 系统安装器；不实现静默安装。

**Reason:** 当前只向少量测试者直接分发 APK，接入应用商店会增加不必要流程，而继续人工发送每版 APK 无法长期使用。复用现有 VPS、共享密钥和零依赖 Python 服务是当前最小闭环；系统安装确认保留 Android 的安全边界。

**Consequences:** 旧 Debug 包需要最后卸载一次。以后每个发布必须提高 `versionCode`，使用同一签名，并把 `server/updates` 单独同步到 VPS。签名库和密码文件不会进入 Git，必须一起离线备份；丢失后不能更新存量安装。普通更新可以稍后安装，清单 `required=true` 时客户端禁止开始新的分析。未来进入应用商店或 Android 开发者验证时，应沿用同一包名和证书所有权。
